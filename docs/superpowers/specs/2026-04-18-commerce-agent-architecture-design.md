# Commerce Agent Architecture Design

Date: 2026-04-18

## Purpose

Commerce Agent is a browser Agent plugin for cross-border ecommerce sellers.
The primary interface is an Agent chat window, not a product management
dashboard. It keeps Page Agent's existing web understanding and browser
operation capabilities, then adds ecommerce-specific tools and structured
result displays.

The first version is architecture-first. It should prove the interaction model,
module boundaries, and extension points without committing to backend services,
ERP push, image search, or broad platform coverage.

## Product Shape

The plugin opens as a side panel with an Agent conversation as the main surface.
Users can either type natural-language requests or click quick action buttons.
Both paths must call the same tool implementations.

The UI has four main regions:

1. Page and Agent status.
2. Conversation message stream.
3. ResultCard Dock fixed above the composer.
4. Quick actions and text composer.

Ordinary assistant messages explain process, decisions, and short feedback.
Structured business results are displayed as ResultCards.

## ResultCard

A ResultCard is a structured result card generated by an AI step or tool call.
It can display information, expose actions, hold state, and become context for
later user requests.

ResultCards are user-facing concepts, not just UI components. The Agent should
be able to reference the active ResultCard when the user says things like
"optimize this title", "use the first image", or "copy the second version".

First-version ResultCard types:

- `product`: product information captured from the current page.
- `listing_copy`: AI-generated title and description variants.
- `task_progress`: multi-step tool or Agent progress.
- `error_report`: recoverable errors, missing fields, unsupported page states.

Reserved ResultCard types:

- `supplier_match`: image or product-based supplier matches.
- `competitor_analysis`: competitor and market-fit analysis.
- `compliance_report`: prohibited word, infringement, or platform-risk checks.
- `erp_push_result`: future ERP push validation and result feedback.

The dock should show the active ResultCard by default and allow expansion into
the current conversation's ResultCard list. This keeps the composer usable while
still supporting multiple structured results.

## First Version Scope

In scope:

- Agent chat side panel.
- Quick action bar above the composer.
- ResultCard Dock with compact and expanded states.
- Local persistence for conversations and ResultCards.
- Amazon product detail page capture.
- Product ResultCard.
- Listing Copy ResultCard.
- AI title and description optimization.
- Task Progress ResultCard.
- Error Report ResultCard.
- Extension points for ERP, backend, image search, and more platforms.

Out of scope:

- Backend service.
- ERP push.
- Real image search or supplier search.
- Batch collection.
- Automatic product publishing.
- Cloud sync.
- Account system.
- Deep support for multiple ecommerce platforms.

## Package Layout

Use new workspace packages with an Agent-oriented name:

```text
packages/
  commerce-agent-core/
  commerce-agent-tools/
  commerce-agent-ui/
  commerce-agent-extension/
```

Workspace package names:

```text
@page-agent/commerce-agent-core
@page-agent/commerce-agent-tools
@page-agent/commerce-agent-ui
@page-agent/commerce-agent-extension
```

This naming keeps the product aligned with its real shape: a commerce-focused
Agent, not a traditional ecommerce backend.

## Module Boundaries

### commerce-agent-core

Protocol and domain boundary package.

Responsibilities:

- ResultCard types, payloads, actions, updates, and validation.
- Conversation message types.
- Tool context and tool result envelope types.
- Source platform types.
- Future ports for backend, ERP, and image search.
- Pure utilities for IDs, timestamps, and lightweight normalization.

Non-responsibilities:

- React components.
- Chrome extension APIs.
- DOM selectors.
- Page Agent runtime calls.
- LLM provider calls.
- ERP or backend implementations.

## Dependency Direction

Allowed dependency direction:

```text
commerce-agent-extension -> commerce-agent-ui
commerce-agent-extension -> commerce-agent-tools
commerce-agent-extension -> commerce-agent-core
commerce-agent-extension -> @page-agent/core
commerce-agent-extension -> @page-agent/page-controller
commerce-agent-extension -> @page-agent/llms

commerce-agent-ui -> commerce-agent-core
commerce-agent-tools -> commerce-agent-core
commerce-agent-tools -> @page-agent/llms
```

Hard constraints:

- `commerce-agent-core` must not depend on UI, Page Agent runtime, Chrome APIs,
  LLM SDKs, backend APIs, or ERP SDKs.
- `commerce-agent-ui` must not capture pages or call tools directly.
- `commerce-agent-tools` must not own chat UI or persistence.
- Existing Page Agent packages should not become commerce-specific.

## Tool Result Routing

Tools should return a structured envelope:

```ts
type ToolResultEnvelope = {
  message: string
  resultCards?: ResultCard[]
  updates?: ResultCardUpdate[]
  events?: ToolEvent[]
}
```

The extension routes `message` into the conversation stream and routes
`resultCards` or `updates` into the ResultCard store. This separates process
feedback from structured business output.

Quick action buttons and natural-language Agent decisions must call the same
tools. For example, clicking "Capture product" and typing "capture this product"
both call `capture_product`.

## Agent Context

The Agent should receive enough structured context to understand references to
current cards:

```ts
type ToolContext = {
  currentPage: PageContext
  activeResultCardId?: string
  resultCards: ResultCard[]
  conversation: ConversationMessage[]
}
```

This allows follow-up commands such as "translate this title into Thai" or "use
the first image" without reparsing chat text.

## Local Persistence

First version should save conversations and ResultCards locally. This avoids
losing captured products when the side panel closes or the browser restarts.

Persistence requirements:

- Store conversation messages.
- Store ResultCards.
- Store active ResultCard ID.
- Store basic settings and feature flags.
- Support schema versioning for persisted state.

Cloud sync is explicitly out of scope.

## First-Version Flow

1. User opens an Amazon product detail page.
2. User opens the Commerce Agent side panel.
3. UI shows Agent chat, quick actions, and empty ResultCard Dock.
4. User clicks "Capture product" or types "capture this product".
5. `commerce-agent-extension` invokes `capture_product`.
6. `commerce-agent-tools` uses the Amazon extractor and current page runtime.
7. Tool returns a message and Product ResultCard.
8. Extension routes the message into chat and the card into ResultCard Dock.
9. User clicks "Optimize listing" or asks for listing optimization.
10. Tool returns Listing Copy ResultCard.
11. User copies a result or continues the conversation.

## Extension Points

Future platform support:

- Add a platform extractor under `commerce-agent-tools/src/platforms/<platform>`.
- Register it with the capture product tool.
- Keep core and UI unchanged unless a new ResultCard type is needed.

Future supplier search:

- Implement `ImageSearchPort` or a supplier-search tool.
- Return `supplier_match` ResultCards.
- Add a renderer in `commerce-agent-ui`.

Future ERP push:

- Implement `ErpPort`.
- Add a push tool.
- Return `erp_push_result` or `error_report` ResultCards.
- Add settings in `commerce-agent-extension`.

Future compliance checks:

- Add a compliance tool.
- Return `compliance_report` ResultCards.
- Keep Product ResultCard unchanged.

## Risks

- Amazon page structure can change. The extractor should combine stable page
  signals where possible and return recoverable error ResultCards when fields
  are missing.
- Full-page DOM extraction can be large. Capture tools should prefer targeted
  extraction over sending the entire simplified DOM to the LLM.
- ResultCard Dock can crowd the composer. Compact, expanded, and detail states
  are required from the first version.
- If quick actions and natural-language commands diverge, maintenance cost will
  double. They must share tool implementations.
- If `commerce-agent-core` imports runtime packages, module boundaries will
  erode quickly. Keep it pure.
